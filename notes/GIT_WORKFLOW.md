# Git Workflow

## Branch ownership

- Do not work directly on `main`. If `main` is selected, warn the user and offer a work branch named `[ai tool]/[sponsor username]/[project work]`, for example `codex/bomcgoni/ai_context_restructure`. Ask for the sponsor username if it is missing.
- On another branch, ask whether it is the intended target. Avoid branching from a work branch. If another branch is needed, warn about nesting and offer `main` as the base.
- The developer chooses branch granularity. A branch may contain one task or several related workloads.
- Branch names record AI tool and sponsor attribution for work performed in non-integrated environments. They do not establish authorship of every change or replace developer review.
- AI tools may commit validated logical changes on the approved work branch. Developers own pushes and integration into `main`.

## Version and deployment identity

`APP_VERSION` is the user-visible release version. Change it only for an intentional visible release. `BUILD_VERSION` is generated by `scripts/prepare-deployment.py` from deployable application content in the staging copy. Documentation, branch names, and commit metadata do not affect it. This makes the deployed cache key deterministic for application content and avoids manual bumps on merges.

Each deployment remains associated with the branch and commit recorded by Git. Preserve that provenance in deployment records or release notes. Do not encode merge count or branch history in the app version: merges can combine branches without changing app content.
